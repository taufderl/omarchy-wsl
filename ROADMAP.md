# Roadmap

Scope and deferred work for `omarchy-wsl`. See [README.md](README.md) for what the project actually is and how to use it, and `PLAN.md` for build-design internals.

## Scope: v1 vs. roadmap

- **v1 (this build): no Hyprland desktop session, but GUI programs already work.** There's no Hyprland/Wayland compositor owning the display — but individual graphical programs launch fine anyway, as their own standalone windows, through WSLg's standard per-app window integration (Xwayland/Weston + FreeRDP RAIL) — the same mechanism any WSL distro gets, no Hyprland involved. Confirmed on real hardware: real Omarchy GUI binaries (`omawrite`, `omacalc`) launch correctly this way with zero Hyprland process running. This is the fully-supported, default target — "no GUI" was never quite the right way to describe it; "no Hyprland desktop" is.
- **Roadmap: nested Hyprland under WSLg**, for a real desktop *session* (a Hyprland compositor owning a whole window, with its own workspaces/bar/etc., rather than one Windows window per app). WSL2's GPU (`/dev/dxg`) supports rendering but not real KMS mode-setting, so Hyprland can't run as it does on bare metal. The viable path is Hyprland running *nested* as a Wayland client inside WSLg's own compositor (`WLR_BACKENDS=wayland`), i.e. as a window inside your Windows desktop rather than owning the physical display. This is designed but intentionally not built yet — see `PLAN.md`'s roadmap section.
- **v1 ships as a `.wsl` file** (`dist/omarchy-v1.wsl`), installed via `wsl --install --from-file` — not `wsl --import`. This turned out not to be optional: `oobe.command` (the mechanism that drives real first-boot provisioning) only fires for the `.wsl`/`wsl --install` install path, confirmed against Microsoft's own docs and on real hardware — see `docs/install-audit.md`'s "Incident #4". A plain tarball for `wsl --import` is still produced (same bytes, `.tar.gz` extension) for inspection, but isn't the supported install path.
  - **Still roadmap, not done**: registering this as an installable-by-name Store-catalog entry (`wsl --install <name>` without `--from-file`, `wsl --list --online` listing) and a proper `.ico` for the Start Menu shortcut. That's a distribution/publishing step, not a functional gap — the file itself already works standalone via `--from-file`/double-click.

### Why no Hyprland desktop in v1

Worth separating two different things this project has sometimes blurred: running a GUI *program* (works today, no roadmap item needed) versus running Hyprland as a full desktop *session* that owns the display (the actual gap, and the roadmap item below).

WSLg gives Linux GUI apps a virtual GPU at `/dev/dxg`, backed by a Direct3D12 Mesa driver stack, for **rendering** — but it does not expose a real `/dev/dri/cardN` with kernel mode-setting. Hyprland's normal DRM backend, which is how it takes ownership of the *whole screen* on real hardware, needs exactly that and doesn't have it; there are documented cases of this failing outright (`dxgkrnl` ioctl errors, GPU detected only as "Microsoft Basic Render Driver"). The only demonstrated way to get a full compositor running under WSLg today is nested inside WSLg's own Weston compositor — a real but different experience from bare-metal Omarchy, which is why it's being built deliberately as an opt-in roadmap item instead of pretended away in v1.

None of that stops an *individual* GUI program from running, though — WSLg's own Xwayland/Weston + FreeRDP integration (the same "RAIL" mechanism every WSL distro gets for free) doesn't need Hyprland, or any compositor of this project's own, to put a single app's window on your Windows desktop. That's already working in v1, unmodified, with no extra integration work on this project's part.
